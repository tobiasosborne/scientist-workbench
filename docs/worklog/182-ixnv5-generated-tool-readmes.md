# 182 — Generated per-tool READMEs (ixnv.5; closes the `ixnv` epic)

**Date:** 2026-05-21.
**Epic:** `scientist-workbench-ixnv` — Registry as single source of truth:
generate & drift-check tool docs. This shard covers child issue
`scientist-workbench-ixnv.5`, the **final** child — and with it the epic
closes.
**Ground truth:** `docs/adr/0043-registry-single-source-of-truth.md`
(Decision 5 is binding and decides the whole approach; Decisions 3 and 6
fix the banner and the drift phase).

## Context

`tools/<name>/README.md` was the last hand-maintained tool-doc surface
the `ixnv` epic had not yet mechanised. Each README restated the tool's
Input / Output / Run / Invariants / Standard-flags blocks — all
mechanical from `def.schema` / `def.examples` / `def.invariants` — and
substantially duplicated the prose of the `tool.ts` literate header. Law
2 ("docs in lockstep with code") was, for these 55 files, still enforced
by human diligence: nothing failed the build when a schema changed and
the README Input block did not.

ADR-0043 Decision 5 resolves the canonical-surface question explicitly:
**the `tool.ts` literate header is canonical; the per-tool README is
generated** — its mechanical sections from `def`, its prose extracted
from the header. The justification is Rule 10: the header *is* mandatory
exposition by law, so making the README a projection of it (rather than
a second obligatory prose surface) halves the Law-2 burden instead of
doubling it. This child implements exactly that decision.

## What changed

**1. The generator (`scripts/gen-tool-readme.ts`).** A literate sibling
of `gen-catalog.ts` and `gen-workbench-barrel.ts`: it walks `tools/` via
`listToolEntries` (already sorted — byte-stability), imports each `def`
(ADR-0010 side-effect-free import), reads the `tool.ts` literate header,
and writes a fully generated `tools/<name>/README.md` carrying the
`AUTOGENERATED:tool-readme` banner.

**2. The header → README extraction contract.** ADR-0043 Decision 5
leaves the marker grammar to this child. The grammar fixed here:

- The literate header is the contiguous `//`-comment block at the top of
  `tool.ts` (line 1 to the first non-comment line — the first `import`).
- Inside it, a *section* is a `Name` line immediately followed by a `-`
  underline — the convention `new-tool.ts` scaffolds and `mod-pow`
  already uses. `=====` banner rules and the title line are stripped;
  text before the first section is the header *lead*.
- The generator recognises exactly **one required section name:
  `Intent`**. A header with no `Intent` section is a **fail-loud error**
  (Rule 1): the generator throws, naming the offending tool and the
  missing section, rather than emitting a silently thin README.
- The README's "How it works" prose is the lead + the `Intent` section +
  **every** section after it, with underlined headers demoted to
  Markdown `###`. Nothing in the header is dropped.

The "require `Intent`, render everything" rule was chosen over a fixed
pull-list of section names because the 55 headers are genuinely
heterogeneous (`Algorithm`, `References`, `Boundary categories`,
`I/O contract`, freeform). A fixed pull-list would silently drop the
sections it did not know — exactly the "silently thin README" failure
the task forbids. Requiring the one anchor and rendering the rest is
robust: a future header section flows into the README automatically, and
a header never written as exposition fails the build.

**3. Schema rendering.** The README's `Input`/`Output` blocks render
`def.schema` to a compact, deterministic type expression — `record {
base: integer, exponent: integer }`, `list<integer>`, `"forward" |
"inverse"`, `tagged "…" record {…}`. The render is a pure function of
the `SchemaNode` tree, so it is byte-stable for an unchanged schema.

**4. Header enrichment — migrate, don't lose (Law 1).** Ten tools had
headers the generator could not parse (no `Intent` section). Each was
normalised, and where the *current* README carried substantive prose not
in the header, that prose was moved into the header (canonical):

- **`cas-simplify`** — the header was stale (claimed "No polynomial GCD"
  while the README documented GCD reduction since v0.3.0 and the 19-rule
  Erf-family identity table since v0.5.0). The header was rewritten with
  `Intent` / `Algorithm` / `Erf-family identities` / `Scope boundary`
  sections absorbing the accurate, current README prose. This was the
  largest single migration — the README was genuinely ahead of the
  header.
- **`cas-verify`** — added an `Intent` section absorbing the README's
  output-shape table and "How" prose (the four record-with-flag shapes,
  the honest-scope note).
- **`expr-parse`** — freeform header rebuilt with an `Intent` section +
  the existing `Grammar` section preserved.
- **`linsolve-q`** — freeform header given a banner + `Intent` section.
- **`hypergeometric-pfq`, `meijer-g-asymptotic-only`,
  `meijer-g-slater-only`, `ntt`, `registry-list`, `special-eval`** — each
  already had rich opening prose and named sections; the opening prose
  was wrapped in an `Intent` section header (a 2-line insertion) so the
  generator's anchor requirement is met. No prose lost.

**5. `check.ts` drift phase ("codegen: per-tool READMEs").** Mirrors the
"codegen: workbench typed barrel" phase exactly: `gen-tool-readme.ts
--check` regenerates every README from the registry and byte-compares
against the committed files, hard-failing with "Run `bun
scripts/gen-tool-readme.ts` and commit the diff" on drift. Placed in the
always-on portion of `check.ts` (before the `if (!QUICK)` gate) per
ADR-0043 Decision 6.

**6. `new-tool.ts`.** Stops scaffolding a hand-authored README. The
scaffold now writes `package.json` + `tool.ts` (with a `summary`
placeholder and the `Intent` literate-header section both generators
require), runs `bun install`, then runs `gen-tool-readme.ts` so a fresh
tool directory carries a generated README from the first commit. The
header prose, the help text, and the closing instructions were rewritten
to say the README is generated — write prose in the `tool.ts` header.

**7. All 55 `tools/*/README.md` regenerated** and the `gen-tool-readme`
script added to root `package.json`.

## Why these choices

**`--check` mode rather than a separate diff in `check.ts`.** The
generator already owns the registry walk and the rendering; teaching it a
`--check` flag (write nothing, exit non-zero on drift) keeps the
drift-detection logic in one place and lets the `check.ts` phase be a
three-line `spawnBun` call — the same shape as the folded-goldens phase.

**The `Input shape` / `Output shape` header sections render into the
README alongside the generated `## Input` / `## Output`.** Mild
redundancy, accepted deliberately: per ADR-0043 Decision 4 the header
sections *explain why* a shape was chosen (canonical exposition), while
the generated blocks *restate* the shape mechanically. Dropping the
header sections would lose the "why"; the generator does not try to
guess which header sections are mechanical.

**`Intent` as the one required anchor.** Requiring exactly one section
keeps the bar low enough that the 45 already-conforming tools needed zero
edits, while still being a real gate: a header with no `Intent` was, in
every one of the 10 cases, either stale or freeform — i.e. a header that
had drifted from the Rule-10 standard. The fail-loud check surfaced that
drift instead of laundering it into a thin README.

## Frictions surfaced

- **`cas-simplify`'s header was materially stale** — it asserted a
  scope ("No polynomial GCD") the tool outgrew two minor versions ago.
  The README, being closer to the agent-facing surface, had been kept
  current; the header had not. This is the strongest single argument for
  Decision 5: with two hand-maintained prose surfaces, one *will* rot,
  and it is not predictable which. One canonical surface, drift-checked,
  removes the question.
- The 55 headers' section structure is **inconsistent** — `Intent`
  present in 46, `Algorithm` in 33, plus `Schema`, `I/O contract`,
  `Boundary categories`, `References`, and freeform blocks. A pull-list
  generator would have been brittle; the "render everything after the
  anchor" rule is what made a single generator handle all 55.

## Acceptance

- `bun run check` — all phases green except the pre-existing
  `packages/bigfloat` complex-Bessel arb-prec timeout (bead
  `scientist-workbench-m9ty`), unrelated to this work.
- The new "codegen: per-tool READMEs" phase passes; regenerating against
  the committed files is a byte-stable no-op (the generator was run
  twice — second run wrote 0 files).
- All 55 `tools/<name>/README.md` carry the `AUTOGENERATED` banner and
  are registry-derived; hand-editing one now fails `check`.
- `gen-tool-readme.ts` fails loud on a header missing `Intent`, naming
  the tool and the section (verified during development against the 10
  unnormalised headers).

## Epic outcome (`scientist-workbench-ixnv`)

With `.5` the `ixnv` epic closes. Across `.1`–`.5` the registry became
the single source of truth for tool-facing docs: the optional `summary`
field on `defineTool` (`.2`); the generated `docs/CATALOG.md` (`.2`,
relocated by `.4`); folded goldens from `def.examples` (`.3`); the `wb`
discovery CLI + Tier-0 README (`.4`); and the generated per-tool READMEs
(`.5`). `check.ts` now carries four codegen drift phases — barrel,
catalog, folded goldens, per-tool READMEs — each mirroring the ADR-0012
pattern, each hard-failing on stale derived docs. Adding a simple tool
now collapses toward editing one file: `tool.ts` (plus a one-line
`summary`); the catalog row, the goldens, and the per-tool README all
regenerate, and the build refuses a stale one. Law 2 is, for tool-facing
docs, mechanically enforced rather than diligence-enforced.
