# 179 — Generated tool catalog + `summary` field (ixnv.2 keystone)

**Date:** 2026-05-21.
**Epic:** `scientist-workbench-ixnv` — Registry as single source of truth:
generate & drift-check tool docs. This shard covers child issue
`scientist-workbench-ixnv.2`, the **keystone** — it unblocks `.4` (the
`wb` discovery CLI) and `.5` (the per-tool README generator).
**Ground truth:** `docs/adr/0043-registry-single-source-of-truth.md`
(Decisions 2, 3, 6, 7 are binding here).

## Context

Adding a tool to the workbench restated its identity across up to seven
hand-maintained surfaces (ADR-0043 Context). The top-level `README.md`
catalog — ~53 hand-copied rows, each `tool | input | output | summary` —
was one of them, and it had already drifted: it was missing rows for
`linsolve-q`, `meijer-g-slater-only` and `qp-solve` (the last never
existed; the `lp-solve` summary referenced a planned-but-absent tool).
Hand-syncing 55 dense rows against 55 `tool.ts` files is exactly the
Law-2 friction the `ixnv` epic exists to mechanise.

ADR-0043 fixes the principle (the registry is canonical; docs are
generated and drift-checked) and `.1` recorded it. `.2` is the keystone
implementation: the `summary` field, the catalog generator, the
`check.ts` drift phase, and the back-fill.

## What changed

**1. The `summary` field (`packages/contract/src/runner.ts`).**
`ToolDefinition` gains an optional `summary?: string`, documented as the
canonical one-line catalog blurb (ADR-0043 Decision 2). `defineTool`
validates it at construction time: a `summary` containing a newline, or
longer than 240 chars, throws loudly (Rule 1 — fail fast, fail loud). A
catalog blurb that wraps or runs long is drift the build should reject,
not silently render.

`ToolMetadata` (`packages/contract/src/registry.ts`) and `describeTool`
gained the `summary` field too, so the registry surface carries it per
ADR-0043 Decision 1 — registry consumers read the canonical summary
without re-opening `tool.ts`. `registry-list` / `registry-search` were
*not* extended to emit it on the wire: their output schemas are closed
and that surface is the discovery-CLI child (`.4`)'s scope; the keystone
generator imports `def` directly and reads `def.summary`, exactly as
`gen-workbench-barrel.ts` reads `def.name`.

**2. The catalog generator (`scripts/gen-catalog.ts`).**
A literate sibling of `gen-workbench-barrel.ts`. It walks `tools/` via
`listToolEntries` (already sorted — that is what makes the output
byte-stable), imports each `def`, and emits a Markdown table into
`README.md` between two `AUTOGENERATED:catalog` HTML-comment markers.
Registered as the `gen-catalog` npm script.

**3. The `check.ts` drift phase ("codegen: README tool catalog").**
Mirrors the "codegen: workbench typed barrel" phase at `check.ts:128`
exactly: read the committed `README.md`, run the generator, byte-compare,
hard-fail with "Run `bun scripts/gen-catalog.ts` and commit the diff" on
drift. Placed in the always-on portion of `check.ts` (before the
`if (!QUICK)` gate) per ADR-0043 Decision 6, so `check:quick` catches
catalog drift in the fast inner loop.

**4. Back-fill.** All 55 tools got a `summary`, each sourced from its
existing README catalog row (the rich prose minus the schema columns and
the trailing "See [tools/…]" link), trimmed to one declarative line
≤240 chars. The three tools missing from the old catalog
(`linsolve-q`, `meijer-g-slater-only`, plus the corrected `lp-solve`
text) got fresh summaries. The generator was then run; `README.md`'s
catalog is now registry-derived.

## Why these choices

**Terse `tool | summary` table, not `tool | input | output | summary`.**
ADR-0043 Decision 3 nominally specifies four columns. But the rich
input/output schema rendering belongs in `tools/<name>/README.md` under
the progressive-discovery model the epic establishes (child `.4`): the
top-level catalog is an *index*, scanned by name, and a reader who wants
the schema follows the link. A `tool | summary` table with a per-row
link out keeps each row to one scannable line and avoids duplicating the
schema rendering that `--schema` and the per-tool README already own.
The task brief explicitly sanctions this reading ("if it underspecifies
the columns, prefer a terse `tool | summary` table with a link").

**Markers as HTML comments carrying the regen command.** `<!--
AUTOGENERATED:catalog — … Regenerate with `bun scripts/gen-catalog.ts`.
-->` and `<!-- /AUTOGENERATED:catalog -->`. HTML comments render
invisibly in any Markdown viewer; the opening marker names its owner so
a human who finds it in source knows what regenerates the region. The
generator splices on the marker strings — everything before the begin
marker and after the end marker is preserved verbatim.

**Length cap enforced in `defineTool`, not `check.ts`.** `defineTool`
runs on every import — the runner, the registry, the generator all
trip it. Validating there means a malformed summary fails the instant
the module is imported, the earliest honest point, consistent with the
existing `checkExamplesAgainstSchema` load-time check.

**Optional field.** ADR-0043 Decision 2 keeps `summary` optional so the
field could land without a flag-day edit. The back-fill makes the point
moot for the current 55 tools, but the optionality is load-bearing for
the next tool added before its author writes a summary — the generator
renders an explicit `_(no summary — add a `summary` field to tool.ts)_`
placeholder rather than an empty cell, so the gap is visible.

## Frictions surfaced

- The old README catalog was a stale projection in a literal sense: it
  carried 53 rows for 55 tools and referenced a `qp-solve` tool that
  does not exist. This is precisely the drift ADR-0043 predicted, and it
  is the strongest single argument for the generator — a hand table
  cannot be trusted even as a back-fill source without cross-checking
  against the live `tools/` walk.
- The `summary` strings could not be mechanically lifted from the old
  rows: the rows mixed schema detail into the prose and trailed a
  boilerplate link. Each summary was hand-trimmed to a clean one-liner.
  That is editorial work, exactly as ADR-0043 Rationale predicts ("a
  catalog blurb is written for a reader scanning fifty rows" — a
  different shape from the literate header).

## Acceptance

- `bun run check` — all phases green except the pre-existing
  `packages/bigfloat` complex-Bessel arb-prec timeout (bead
  `scientist-workbench-m9ty`), which is unrelated to this work.
- The new "codegen: README tool catalog" phase passes; regenerating
  against the committed `README.md` is a byte-stable no-op.
- The "codegen: workbench typed barrel" phase still passes (the
  `runner.ts` / `registry.ts` edits did not perturb the barrel).
- All 55 `tool.ts` files carry a `summary`; all ≤240 chars, all single
  line; `defineTool`'s validation accepts every one.
- `README.md`'s catalog is generated and drift-checked; hand-editing it
  now fails `check`.
