# ADR-0043 — The tool registry is the single source of truth for tool-facing docs

**Status:** Accepted — 2026-05-21. Proposed 2026-05-21.
**Beads:** `scientist-workbench-ixnv` (epic — Registry as single source of
truth: generate & drift-check tool docs). This ADR is child issue
`scientist-workbench-ixnv.1` and is the Law 1 gate for the four
implementation children: `.2` (generated catalog + `summary` field —
keystone), `.3` (goldens-from-examples), `.4` (`wb` discovery CLI + tiered
README), `.5` (generated per-tool README skeleton).
**Related:** **ADR-0012** (typed-barrel codegen — the precedent this ADR
generalises; `packages/compose/src/generated/wb.ts` is regenerated and
byte-compared in `scripts/check.ts:128`), ADR-0010 (every tool exports a
pure-data `def`; `import.meta.main`-gated `runTool` — the property that
makes the registry importable without spawning), ADR-0004 (`S.*` schema
constructors; `--schema` emits a real wire-form `Schema`), ADR-0011 (typed
flags; standard-flag merge layer — `--schema` / `--examples` /
`--invariants` / `--version` are standard flags every tool answers),
PRD-v0.2.md §6.1 (the seven-artefact contract; examples-per-code-path
guidance).

---

## Context

Adding one simple tool to the workbench today restates the tool's identity
across as many as seven hand-maintained surfaces:

1. the literate header of `tools/<name>/tool.ts` (prose intent, input/output
   shape, algorithm sketch — Rule 10);
2. `def.examples` inside the same `tool.ts` (worked input/output pairs);
3. `tools/<name>/goldens.spec.ts` (`export const goldens: GoldenSpec[]`);
4. `tools/<name>/README.md` (agent-facing summary, Input/Output/How/
   Invariants/Run/Standard-flags sections);
5. the catalog row in the top-level `README.md` (`tool | input | output |
   summary`);
6. a paragraph in `PRD-v0.2.md` when the tool introduces a value-protocol
   convention;
7. an invocation line in `scripts/demo-scope.sh`.

`scaffold` (`scripts/new-tool.ts`) emits skeletons for 1, 3, and 4; the
rest are pure copy-discipline. Law 2 — "docs in lockstep with code" — is
today enforced *by human diligence* across all seven. When a tool's schema
changes, a developer must remember to re-edit the README Input block, the
catalog row, and possibly the goldens. Nothing fails the build when they
forget. The catalog rows in `README.md:107-162` already drift: several
carry multi-sentence prose that restates what the tool's `--schema` and
literate header already say, and keeping ~40 such rows synchronised with 40
`tool.ts` files by hand is exactly the friction this epic targets.

The root cause of both the "tedious to add a tool" friction and the "heavy
README" friction is the same: **tool-facing docs are hand-copied from
information the registry already exposes mechanically.** Every tool answers
`--schema`, `--examples`, `--invariants`, and `--version` (ADR-0011's
standard-flag layer). `tools/registry-search/tool.ts` and
`tools/registry-list/` already decode that wire output and query it:
`registry-search` uses `schemaTopKind`, `schemaMentionsKind`, and
`schemaExpressionHead` to filter tools by input/output kind. The registry
*is* the structured database of tool identity; the hand-written docs are a
stale, manually-maintained projection of it.

The workbench has already solved this exact problem once, for code rather
than docs. ADR-0012's typed barrel `packages/compose/src/generated/wb.ts`
is generated by `scripts/gen-workbench-barrel.ts` — which walks `tools/`,
imports each `def`, and emits a TS module — and `scripts/check.ts:128`
("codegen: workbench typed barrel" phase) regenerates it and byte-compares
against the committed file. A stale barrel fails `bun run check` with a
named remediation (`Run \`bun scripts/gen-workbench-barrel.ts\` and commit
the diff`). Drift is mechanically impossible to commit-and-forget. This ADR
records the decision to apply the *same pattern* to tool-facing docs.

---

## Decision

We pin the following convention. It is the principle the whole `ixnv` epic
rests on; the four implementation children build the generators and the
drift phases, but they implement *this* decision — they do not get to
re-litigate it.

### Decision 1 — The registry is the single source of truth for tool-facing docs

Each tool's machine-readable metadata is the **canonical** record of its
identity. That metadata is, per the `ToolDefinition` interface
(`packages/contract/src/runner.ts:217`):

| Field | Today | Role as source of truth |
|---|---|---|
| `name` | `def.name` | tool identity; catalog row key; README `#` heading |
| `version` | `def.version` | catalog/README version surface |
| `schema.input` / `schema.output` | `def.schema` (ADR-0004 `S.*`) | the Input/Output sections of every derived doc; the catalog `input`/`output` columns |
| `examples` | `def.examples` | the worked input/output pairs; the source for goldens (Decision 3) |
| `invariants` | `def.invariants` | the README Invariants section |
| `arbprec` / `numerical` / `nondeterministic` | determinism-tier flags | the standard-flag note + tier annotation in derived docs |
| **`summary`** | **NEW — see Decision 2** | the one-line catalog `summary` column; the README opening line |

No generator may read a hand-maintained static list of tools, a static
catalog table, or a static head vocabulary. Every generator walks `tools/`,
imports each `def` (ADR-0010 makes this side-effect-free), and reads the
fields above — exactly as `gen-workbench-barrel.ts` already does.

### Decision 2 — A new optional `summary` field on `defineTool`

`ToolDefinition` (`packages/contract/src/runner.ts:217`) gains one new
**optional** field:

```ts
  /**
   * A single declarative sentence — the tool's catalog blurb. One line,
   * no trailing period required, ≤ ~240 chars. Generated docs use it as
   * the catalog `summary` column and the README opening paragraph. When
   * absent, generators fall back to the first sentence of the tool.ts
   * literate header (Decision 4). Authoring it explicitly is preferred:
   * the fallback is a migration convenience, not a destination.
   */
  summary?: string;
```

It is optional so the field can land (child `.2`) without a flag-day edit
to all ~40 tools, and so the keystone generator ships before every tool has
been back-filled. The implementation child decides the exact length bound
and whether `check.ts` warns on absence; this ADR fixes only that the field
exists, is one line, and is the canonical catalog blurb.

`summary` is *not* a duplicate of the literate header. The header is a
multi-paragraph chapter (Rule 10); `summary` is the one-line index entry.
The relationship is the same as a book's chapter title versus its opening
section — both hand-written, neither generated from the other, related only
by editorial intent.

### Decision 3 — Which docs become *generated*

The following carry a generated-file banner (the same
`AUTOGENERATED — do not edit by hand. / Regenerate with \`...\`` banner
`gen-workbench-barrel.ts` already emits at `wb.ts:120-122`) and are **never
hand-edited**:

1. **The top-level catalog table** (`README.md:107-162` today). Each row is
   `name | input-schema-rendering | output-schema-rendering | summary`,
   derived entirely from `def.name`, `def.schema`, and `def.summary`. The
   input/output columns render the wire `Schema` to a compact human form
   (the same decode `registry-search` already performs). Child `.2` owns
   this generator; it is the keystone because the other three children
   reuse its registry-walk and schema-render helpers.

2. **The mechanical sections of each `tools/<name>/README.md`** — the
   `Input`, `Output`, `Run`, `Invariants`, and `Standard flags` blocks.
   These are pure restatements: `Input`/`Output` render `def.schema`;
   `Invariants` renders `def.invariants`; `Run` is a templated `echo … |
   bun tools/<name>/tool.ts` line built from the first example; `Standard
   flags` is a constant. Child `.5` owns this generator.

3. **The goldens** — `tools/<name>/goldens/*.golden.json`, folded from
   `def.examples`. Every example is, by construction, a known-correct
   input/output pair; it is already a golden. Child `.3` owns the
   examples→goldens fold. (`goldens.spec.ts` may remain a hand-authored
   *supplement* for inputs an author wants exercised beyond the examples —
   that is an implementation-child decision; this ADR fixes only that
   examples are *a* source of goldens, automatically.)

### Decision 4 — Which docs stay *hand-written*

Generation covers **mechanical restatement only**. The following remain
fully hand-authored prose and are never touched by a generator:

- the literate header of every `tools/<name>/tool.ts` (Rule 10 — the
  chapter a fresh reader reads top-to-bottom);
- the **"How" / "Why"** prose block of each `tools/<name>/README.md` (the
  algorithm narrative, scope boundary, reference citations) — see
  Decision 5 for how this coexists with the generated sections;
- all ADRs under `docs/adr/`;
- all worklog shards under `docs/worklog/`;
- the `PRD-v0.2.md` convention paragraphs.

The dividing line is bright: if a piece of text *restates* `def` fields, it
is generated; if it *explains* the tool — why it is shaped the way it is,
what pitfalls motivated a defensive check, which paper it ports — it is
hand-written. A generator that tried to author the "Why" prose would be
producing exactly the terse, intent-free text Rule 10 forbids.

### Decision 5 — `tool.ts` literate header is canonical; the per-tool README is generated

This resolves the open question the issue body raises explicitly: *is
`tools/<name>/README.md` or the `tool.ts` literate header the canonical
prose surface?*

**The `tool.ts` literate header is canonical. The per-tool README is
generated** — its mechanical sections from `def` (Decision 3), and its
prose block extracted from the `tool.ts` header (the `Intent` / `Algorithm`
exposition). The README becomes a derived artefact carrying the generated-
file banner; hand-edits to it are a drift-check failure.

The justification rests directly on Rule 10. Rule 10 mandates that
`tool.ts` source files *are* exposition — "a fresh reader should read
`tool.ts` top-to-bottom like a chapter." That makes the literate header
load-bearing prose that *must* exist and *must* be maintained, by law,
regardless of any decision here. If the README were instead canonical, the
workbench would carry *two* obligatory hand-maintained prose surfaces per
tool saying substantially the same thing — and Law 2's lockstep burden
would double rather than halve. Picking the header as canonical means there
is exactly one place an author writes and maintains tool prose, and Rule 10
already requires that place to be excellent.

The mechanics: a tool's `tool.ts` header uses lightweight section markers
already conventional in the existing templates (`Intent`, `Input shape`,
`Output shape`, `Algorithm` — see `scripts/new-tool.ts:187-212` and
`tools/mod-pow/tool.ts:1-33`). The README generator extracts the `Intent`
and `Algorithm` prose for the README's "How/Why" block and composes the
mechanical sections from `def`. The exact marker grammar and extraction
rule are the implementation child's (`.5`) to fix; this ADR fixes only the
*direction*: header → README, never README → header.

A consequence worth stating: this slightly raises the bar on `tool.ts`
header discipline, because the header is now the *only* prose source and
its `Intent`/`Algorithm` sections are reader-facing in two places. That is
the intended effect — it concentrates editorial effort on the surface Rule
10 already declares mandatory, rather than splitting it.

### Decision 6 — `check.ts` gains drift phases

`scripts/check.ts` gains drift phases, one per generated artefact class,
each **mirroring the "codegen: workbench typed barrel" phase at
`scripts/check.ts:128`** exactly:

1. read the committed generated file(s) into memory;
2. run the generator;
3. byte-compare; any difference is a failed phase whose `detail` names the
   generator to re-run and to commit (`Run \`bun scripts/<gen>.ts\` and
   commit the diff`).

The phases to add (one per implementation child's generator): catalog
drift, per-tool README drift, goldens-from-examples drift. They run in the
*always-on* portion of `check.ts` (before the `if (!QUICK)` gate at
`check.ts:164`) so `bun run check:quick` catches drift too — drift detection
is cheap (a registry walk + string compare) and belongs in the fast inner
loop, exactly as the barrel phase does.

This is the load-bearing decision: it is what converts Law 2 from a rule
enforced by human memory into a rule enforced by the build. After this ADR's
epic ships, a stale derived doc cannot be committed without
`bun run check` going red, just as a stale `wb.ts` cannot today.

### Decision 7 — Generated files are committed, not gitignored

Every generated artefact (catalog section of `README.md`, each per-tool
`README.md`, the folded `goldens/*.golden.json`) is **committed to git**,
following ADR-0012's deviation rationale (`gen-workbench-barrel.ts:25-40`):
committing keeps a fresh clone's docs correct without a generation step,
makes drift visible in `git status` / `git diff` alongside the code change
that caused it, and costs only the diff. A gitignored README would leave a
fresh clone with no tool docs until the first `check` run — unacceptable for
docs whose whole purpose is to be readable.

## What we will not decide here

- **The exact schema-rendering format** for the catalog `input`/`output`
  columns and the README `Input`/`Output` blocks. Child `.2` chooses the
  human-readable rendering of a wire `Schema`; it must be deterministic
  (byte-stable for an unchanged schema) but its surface form is an
  implementation detail.
- **Whether `goldens.spec.ts` survives** as a hand-authored supplement or
  is fully subsumed by examples. Child `.3` decides. This ADR fixes only
  that examples *are* automatically a source of goldens.
- **The `wb` discovery CLI surface and the Tier-0 README shrink.** Child
  `.4` owns the progressive-discovery model (`bun wb` for discovery, a
  ~30-line bootstrap README). This ADR establishes the registry-as-truth
  principle the CLI rests on but does not design the CLI.
- **The `tool.ts` header marker grammar.** Child `.5` fixes the exact
  section-marker convention the README generator parses.
- **`demo-scope.sh` generation.** The demo script stays hand-authored for
  now — a demo invocation is an editorial choice about what to showcase,
  closer to "Why" prose than to mechanical restatement. A future ADR may
  revisit if the registry grows a representative-invocation field.
- **Retrofitting `summary` onto every existing tool.** The field is
  optional precisely so back-fill is incremental; whether `check.ts` warns
  on a missing `summary` is child `.2`'s call.

## Rationale

### Why registry-as-truth rather than README-as-truth

The registry metadata is *already* the structured, machine-validated record
of tool identity: `def.schema` is validated by the runner on every
invocation; `def.examples` are exercised as goldens; `def.invariants` are
checked by `--test` hooks. Hand-written docs have none of these
correctness pressures — nothing validates a README Input block against the
real schema. Making the validated artefact canonical and the docs derived
means the docs inherit the registry's correctness for free. The inverse
(docs canonical, registry derived) is incoherent: you cannot derive a
runner-validated `S.*` schema from English prose.

### Why mirror ADR-0012's pattern exactly rather than invent a new one

The typed-barrel codegen has been in production since ADR-0012 and the
drift phase at `check.ts:128` has caught real drift (a new tool added
without regenerating `wb.ts`). The pattern — walk `tools/`, import `def`,
emit, byte-compare in `check` — is proven, understood by every agent who has
read `check.ts`, and already has the `findToolsRoot` / `importToolDef`
helpers (`gen-workbench-barrel.ts:45`) the new generators reuse. Inventing a
second drift-check mechanism would be gratuitous divergence. The new
generators are siblings of `gen-workbench-barrel.ts`, not a new species.

### Why the header is canonical — the Rule 10 argument restated

Rule 10 is not optional and not negotiable: `tool.ts` headers *are*
exposition and *will* be maintained as excellent prose. Given that fixed
constraint, the only question is whether the README is a *second*
obligatory prose surface or a *projection* of the first. A second obligatory
surface doubles the Law 2 burden this epic exists to halve. A projection
adds zero new maintenance obligation. The choice makes itself once Rule 10
is taken as given.

### Why `summary` is a new field rather than "first sentence of the header"

A header's first sentence is written for a reader entering a chapter; a
catalog blurb is written for a reader scanning forty rows. They have
genuinely different editorial shapes — the catalog row often needs to name
the algorithm, the determinism tier, and the scope boundary in one
declarative line (see the existing dense rows at `README.md:113-114`), which
is not how a chapter opens. A dedicated optional field lets the author write
the right sentence for the index without distorting the header. The
"first-sentence fallback" exists only so the catalog never has an empty
cell during incremental back-fill.

## Consequences

**Positive.**

- Adding a simple tool collapses toward editing one file: `tool.ts` (plus a
  one-line `summary`). The catalog row, the per-tool README skeleton, and
  the goldens regenerate. This is the epic's headline acceptance criterion.
- Law 2 becomes mechanically enforced for tool-facing docs. "Code shipped
  with stale docs is incomplete work" stops depending on an agent
  remembering — `bun run check` goes red.
- The catalog stops drifting: ~40 hand-maintained rows become one generated
  table.
- A single canonical prose surface per tool (the `tool.ts` header)
  concentrates the editorial effort Rule 10 already mandates.

**Costs and risks.**

- The `tool.ts` literate header becomes load-bearing in a stricter sense:
  it is now the sole prose source, surfaced in two rendered places. Header
  quality matters more. This is intended (it concentrates effort where Rule
  10 wants it) but it does raise the bar on header reviews.
- Every generated file must carry the banner and resist hand-editing.
  An agent who edits a generated README "just this once" will hit a drift
  failure — which is the design working, but it is a new failure mode to
  learn. The banner text must be unambiguous.
- The drift phases add three registry walks to `check:quick`. Each is a
  directory walk plus `def` imports — the barrel phase already pays this
  cost once; three more are cheap but not free. Acceptable for the inner
  loop.
- `scripts/new-tool.ts` must change: it should no longer scaffold a
  hand-edited `README.md` (that becomes generated) and should scaffold a
  `summary` placeholder in the `defineTool` call. That edit belongs to
  child `.5` / `.2`, not this ADR, but it is a foreseeable consequence.
- ADR-0012's deviation note about committing generated files applies
  verbatim; the new generated files inherit the same "regenerate is a
  no-op when nothing changed" byte-stability requirement. A generator that
  is not byte-stable would make every `check` run red — the generators must
  sort their registry walk (as `gen-workbench-barrel.ts:75-79` does).

## Alternatives considered

**A. Keep docs hand-written; rely on Law 2 diligence.** The status quo. The
epic exists because this does not scale: forty tools, seven surfaces each,
and a drift the catalog already exhibits. Rejected — it makes Law 2 a hope,
not a guarantee.

**B. README canonical, header generated from it.** Symmetric to Decision 5
but inverted. Rejected against Rule 10: the header is mandatory exposition
*by law* and must be hand-maintained regardless; deriving it from a README
would either violate Rule 10 (a generated header is not literate
exposition) or leave both surfaces hand-maintained. Either outcome fails the
epic's goal.

**C. Both header and README hand-written; only the catalog and goldens
generated.** A partial measure — generate the cheap surfaces, leave the two
prose surfaces hand-synced. Rejected because the per-tool README *is* one of
the seven surfaces driving the friction, and its Input/Output/Invariants
blocks are pure mechanical restatement. Leaving it hand-written keeps half
the lockstep burden. The "How/Why" prose genuinely is hand-written — but it
should be hand-written *once*, in the header (Decision 5), not twice.

**D. A separate `lint`/`docs-check` script rather than `check.ts` phases.**
Rejected for the same reason ADR-0012 put the barrel drift check inside
`check.ts`: a separate script is one more thing to remember to run, which is
exactly the human-diligence failure mode this ADR removes. Drift detection
must be a phase of the one gate (`bun run check`) every agent already runs.

**E. Drift phases warn rather than fail (like the raw-kind-literal phase at
`check.ts:111-117`).** Rejected. A warning is advisory; stale docs would
still be committable, and Law 2 would still be diligence-enforced. The
barrel phase fails hard (`check.ts:140-147`); the docs phases must too. The
raw-kind-literal phase warns because its check is heuristic and prone to
false positives — the docs drift check is an exact byte-compare with zero
false positives, so hard failure is correct.

## Acceptance

This ADR is *accepted* when:

- This document is committed under `docs/adr/0043-*.md`.
- `CLAUDE.md`'s Law 2 section cross-references it (a derived tool doc is
  generated and drift-checked per ADR-0043).
- The four implementation children (`ixnv.2`–`.5`) lose their `blocked-by`
  edge on `ixnv.1` and become claimable.

The *convention* this ADR pins is *implemented* when the `ixnv` epic
closes:

- `defineTool` carries the optional `summary` field.
- A new simple tool requires editing only `tool.ts` (+ a one-line
  `summary`); catalog row, per-tool README skeleton, and goldens
  regenerate.
- `scripts/check.ts` has catalog-drift, per-tool-README-drift, and
  goldens-from-examples-drift phases, each mirroring `check.ts:128`, each in
  the always-on (non-`QUICK`-gated) portion.
- Every generated artefact carries the `AUTOGENERATED` banner; no generated
  artefact is hand-edited; every generator walks the registry and never
  reads a static tool list.
- `README.md`'s catalog is generated; the file shrinks toward a Tier-0
  bootstrap with discovery flowing through `bun wb` (child `.4`).
